## 2. 配点(pointWeight)機能の完全撤廃

### 経緯
ユーザーから「配点というのがやっぱりなんとも扱いにくい、入力させなくても章の数で均等に分配すればいい」という要望が来た。

1. **1回目のceo相談**：完全な均等配分には反対、「テストでの重要度：高い/ふつう/低い」の3択セレクトへの妥協案を推奨（配点による優先度メリハリという価値提案は残すべき、という理由）。
2. **ユーザーの再反論**：「配点は生徒がどこから情報を取ってくるの？過去問なんかは基本ない。大学生じゃあるまいし」「理解度・自分の進み具合・残り時間の総合判断こそがこのアプリの強み」。3択セレクトも結局は生徒が知り得ない情報を答えさせている点で数値入力と本質的に同じ、という指摘。
3. **2回目のceo相談**：前言撤回。「3択も所詮は生徒が持ってない情報の主観申告。配点由来の重みは完全廃止すべき。優先度は理解度不足×テストの近さのみでよい」に転換。「切る候補」も配点効率ではなく残り所要時間が長い順にすべき、との助言。
4. **CTO相談との整合性チェック**：CTOは技術的実装案として「同一教科内の章の数で100点を按分」を提案していたが、実装担当（Claude）が`generateTodayPlan`のコードを実際に読み、この関数が全教科の章を1つのリストにまとめてスコア降順ソートしていること（教科ごとの配分ではなく教科横断比較）を確認。「教科内で100点按分」方式だと、たまたま章の登録数が少ない教科（例：3章なら1章33点）が、章を多く登録した教科（例：10章なら1章10点）より不当に優先されるという新しいバイアスが生まれると判明。この副作用を避けるため、按分ではなく**配点由来の重み自体を優先度計算から完全に除去**する設計に変更した。

### 最終的な設計
- `priority = max(target − decayedUnderstanding, 0) × proximity`（配点の乗算項を削除）。
- `subtopicPriority`も同様（`teacherHinted`ブーストは配点と無関係の実在シグナルなのでそのまま維持）。
- `buildReasons`/`buildSubtopicReasons`から「配点が高め」チップを削除。
- `TriageCandidate.efficiency`（配点÷残り時間）→ `totalMinutesNeeded`（残り所要時間そのもの）に変更、降順ソート（残り時間が長いものほど「切る候補」）。
- `Chapter.pointWeight`フィールドを型から削除。後方互換シムは書かない（既存localStorageに残る`pointWeight`プロパティは実行時に単に無視される）。

### 実装後レビューでの修正
- `.triage-efficiency`に`white-space: nowrap`が残っており、新しい長めの文言（「残り約N時間M分かかる見込みです（他の項目より時間がかかるため、優先度を下げる候補です）」）がスマホ幅で見切れる懸念 → `overflow-wrap: break-word`に変更。
- 見出し文言「時間配分の効率上」が新しい単純な「残り時間が長い順」ロジックと微妙にニュアンスがずれていたため、「時間がかかる項目は他を優先するため」に統一。
- オンボーディングの配点欄専用だった孤立CSS（`.chapter-draft-row .field.inline input`）を削除。

commit: `b3cf578`。テスト344件パス。Playwright実機確認済み（オンボーディング・今日・理解度・設定の4画面すべてで「配点」の文言が完全に消えていることを確認）。

## Takeaway（今後のプロダクト判断に活かすこと）

- **生徒（中高生の定期テスト）が構造的に知り得ない情報を入力させる機能は、入力形式（数値/選択式/スライダー）をどう変えても本質的な問題は解決しない。** 今後似た提案（重要度・難易度予想の自己申告など）が出たら、まず「生徒は本当にこの情報を知っているか」を問うこと。
- **サブエージェントの技術提案も、コードを実際に読んで検証すること。** 今回、CTOの実装案（教科内按分）をそのまま実装していたら、教科横断比較で新しいバイアスを生む欠陥に気づかないまま実装が進んでいた。
