4. **P1実装中に見つけた重大な問題**: 3のアコーディオンを最初`<details><summary>`で実装したが、**Playwrightのクリック・タップ操作（headless/headed問わず）でネイティブトグルが反応しない**ことを実際に動かして発見した。キーボード操作（Enter/Space）では正常にトグルするため要素自体は生きているが、指でタップして使う中高生向けアプリとして致命的と判断し、`useState` + `<button aria-expanded>` による自前アコーディオンに書き直した（`Settings.tsx`）。
5. **追加で見つけたバグ**（commit `870fa6b` 以前、`ChapterCurriculumSuggest.tsx`）: 候補ドロップダウンの「外側タップで閉じる」検知が`mousedown`イベントで、閉じる際にレイアウトが縮む（他要素を押し下げていた分が戻る）ため、同じ指の動作の`mouseup`が別の位置に着地し、直後にタップしたかった別のボタンへの**最初のタップが吸収される**現象を発見。`mousedown`ではなく`click`イベントで外側判定するよう変更して解消。
6. **実機で発見されたバグ**（commit `870fa6b`）: `SessionRecord.tsx`の「かけた時間（分）」入力欄が、`onChange`のたびに`Math.max(1, Number(value))`をその場適用していたため、値を消そうとすると即座に1へ強制されて消せなかった（ユーザーが実機スクリーンショット付きで報告）。入力中は空文字列を許容し、保存時(`handleSave`)にのみ最低1分へ補正する方式に修正。

## 技術的な学び（今後のために残す）

- **`<details>/<summary>`のネイティブトグルは、Playwrightの合成クリック/タップで反応しないことがある**（キーボードのEnter/Spaceでは動く）。プレーンHTMLでは動く、React 18アプリでは動かない、というのもこのセッションで確認済み（原因までは特定していない）。**今後アコーディオンUIを作る際は`<details>`を避け、`useState` + `<button>`で実装すること。**
- **数値inputで`onChange`のたびに`Math.max(min, Number(value))`をその場適用するパターンは、ユーザーが値を一度空にして打ち直す操作を妨げる。** 空文字列は許容し、min補正は保存時（またはonBlur）にのみ行うこと。今回`SessionRecord.tsx`のminutesで発生。**他の数値input（章の配点入力など）に同じパターンが残っていないか、まだ横展開チェックをしていない** — 次回時間があれば確認するとよい。
- 実際に動かして確認する際、Playwrightの`click()`が「見た目は成功したのに実際にはイベントが届いていない」ケースがある。疑わしいときは`aria-expanded`などの状態値をJSで直接確認し、`document.elementFromPoint`で実際にその座標に何があるかも合わせて確認すると切り分けが早い。

## デプロイ障害インシデント（重要、次回も起こりうる）

**発見**: ユーザーが本番URL（`https://ssei59386.github.io/pomodoro-timer/`）にアクセスしたところ「最初期ぐらいの出来」と報告。調査の結果、**2026-07-02以降、`claude/app-dev-per-plan-qur753`ブランチへのpushによるGitHub Pagesデプロイが全部失敗していた**ことが判明（最後に成功していたのは`master`の2026-06-30時点のコミット）。つまり見通し機能Phase1〜6・オンボーディングウィザード化を含む、7/2〜7/6の全作業が一度も本番に反映されていなかった。

**原因**: GitHub Environment `github-pages` の「Deployment branches and tags」制限が `master` のみ許可になっており、`claude/app-dev-per-plan-qur753` からのデプロイが弾かれていた（deployジョブが1秒未満でsteps空のまま失敗、というのが典型パターン）。ユーザーがGitHubのSettings > Environments > github-pages でこのブランチを許可リストに追加して解消。

**副次的に判明した不安定さ**: ブランチ制限を解消した後も、**buildジョブは毎回一発成功するのに対し、deployジョブ（`actions/deploy-pages@v4`ステップ）が`"Deployment failed, try again later."`という一時的なエラーで失敗することが2回連続で観測された**（それぞれ空コミットで即リトライしたら通った）。原因はGitHub側のインフラ的な一過性の問題と思われるが、確定はしていない。**今後もpush後は`curl -sI <URL>`の`Last-Modified`ヘッダーか、`https://api.github.com/repos/ssei59386/pomodoro-timer/actions/workflows/deploy-pages.yml/runs`（`gh`未認証でも公開リポジトリなら見える）で反映を確認し、deployだけ失敗していたら空コミットでリトライする運用でよい。**

## 複数端末同期についての検討（結論: 今はやらない、未実装）

ユーザーから「進行状況を保存するシステムは作れるか」と質問があり、確認したところ「弟がスマホとPCなど複数端末で使いたい」というニーズだった。CEO・CTOに相談し、以下で一致：

- **CEO判断**: やらない。ユーザーはまだ弟1人で、複数端末ニーズが本当に深刻か検証されていない段階でバックエンド・ログイン基盤に投資するのは、Phase 0の「バックエンドなし」の原則を壊す割に合わない判断。
- **CTO判断**: 技術的にもBaaS導入（Firebase/Supabase等）は`store.tsx`の同期的な状態更新モデル（`loadData`/`saveData`が同期関数である前提）を非同期パイプラインに作り替える本質的なアーキテクチャ変更になり、過剰実装。
- **代替案（両者一致、まだ未実装）**: `Settings.tsx`に「データを書き出す（JSONダウンロード）」「読み込む（アップロード）」ボタンを追加するだけの軽量な手動同期。`storage.ts`の`saveData`/`loadData`は無改造で済む見込み。弟が実際に何度も不便を感じるようなら、その時初めて自動同期を検討する。

**次回このニーズが再燃したら、まずこのエクスポート/インポート機能から着手すること。**
