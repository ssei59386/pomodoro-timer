### Confirmed design decisions (via AskUserQuestion, 2026-07-02, do not re-ask)

1. **配点 (pointWeight) stays at chapter level**, not re-collected per subtopic — user's own pushback made this concrete: "students wouldn't realistically know exam point weight at that granularity anyway." Subtopic-level priority scoring shares/divides the chapter's existing `pointWeight` rather than asking for a new per-subtopic input.
2. **Problem count input is exactly 2 fields**: "基礎問題数" (sum of textbook worked-examples + workbook basic-tier problems) and "発展問題数" (sum of textbook + workbook advanced-tier problems) — explicitly not 4 separate textbook/workbook fields, but the UI copy must make clear what to count in each of the 2 fields.
3. **Curriculum reference fuzzy-match**: real-time suggest-as-you-type while entering a subtopic name (not a separate "browse reference data" button/modal).
4. **Ideal pace display**: time-based (cumulative minutes invested vs. cumulative minutes that should have been invested by now), expressed as a handful of concrete "state" tiers per user's own framing (e.g. something like "on pace for basic-level mastery, behind on advanced-level") rather than a bare understanding-percentage gap. Exact tier count/labels/thresholds were left to technical judgment — see Phase 4 below. **(Later superseded — see "Phase 4 design decision" below: the user overrode this time-based framing itself in favor of achievement-based judgment.)**

### Full design (converged through CEO/CTO consult + a dedicated Plan-agent design pass, 2026-07-02)

- **Understanding tracked at subtopic level only** — no chapter-level rollup/averaging is built. Chapters without subtopics keep working exactly as today (existing `Chapter.understanding`/`priority()`/`generateTodayPlan()` untouched) — this is a deliberate dual-path design so chapters where a student hasn't bothered breaking into subtopics don't regress or become mandatory-input.
- **pointWeight sharing**: chapter's existing `pointWeight` is divided evenly across its subtopics for scoring purposes (`pointWeight / subtopics.length`), so the sum across a chapter's subtopics always equals the chapter's pointWeight — this preserves cross-chapter comparability (the thing that would break if each subtopic just re-used the full chapter weight).
- **Time estimate formula**, per subtopic, split into 2 tiers (basic/advanced) rather than one merged number:
  ```
  remainingRatio = 1 − decayedSubtopicUnderstanding(subtopic, today)
  conceptMinutes = (understanding < 0.2) ? CONCEPT_LEARNING_COST_MINUTES /* placeholder 20 */ : 0
  basicMinutes = (basicProblems ?? 0) × MINUTES_PER_BASIC_PROBLEM /* later revised, see below */ × remainingRatio
  advancedMinutes = (advancedProblems ?? 0) × MINUTES_PER_ADVANCED_PROBLEM /* later revised, see below */ × remainingRatio
  ```
  `conceptMinutes` only applies below the 0.2 understanding threshold (not every time) to avoid re-charging the concept cost on every re-estimate. `difficultyLevel` (from curriculum reference matching) is deliberately *not* folded into this formula yet — mixing it with problem-count would double-count and make the formula hard to tune; it's kept as informational/suggestion-only for now.
- **Curriculum fuzzy-match utility**: `src/data/curriculumSearch.ts` (see "Phase 1 current implementation state" — already built) unifies `mathCurriculumReference` (array export) and the 12 per-file science exports (`scienceCh1`/`scienceCh2`/`scienceCh3`/`sciencePhysicsBase`/`sciencePhysics`/`scienceChemistryBase`/`scienceChemistry`/`scienceBiologyBase`/`scienceBiology`/`scienceEarthScienceBase`/`scienceEarthScience`) into one flat, memoized, normalized (NFKC + whitespace-stripped + lowercased) search index, exposing `searchCurriculumSubtopics(query, { subject?, limit? })` with prefix-match scoring boost.
- **Session recording granularity (decided, not yet built — Phase 2)**: sessions target a specific subtopic directly (`StudySession.subtopicId?`), not chapter-level with heuristic distribution — chosen over the distribute-heuristically alternative because the user's stated preference is precision/rigor over lower input friction. Chapters without subtopics keep recording at chapter granularity (`subtopicId` stays undefined) — same dual-path principle as above.
- **Pace tiers (Phase 4, not yet designed in full at the time this was written)**: time-based ratio of actual-cumulative-minutes-invested vs ideal-cumulative-minutes-by-today, classified into tiers (e.g. ahead/on_track/behind/critical draft from the Plan-agent pass, thresholds are placeholders). **Open question carried into Phase 4**: what "today" is measured against — a per-subtopic registration date anchoring a straight-line pace from registration to test date, vs. a moving 7-day window (registration-date-free, simpler) — Plan-agent flagged both as viable, not decided yet. **(This question became moot — see "Phase 4 design decision" below.)**
- **Off-track threshold**: cumulative point-weight impact, not any single lagging subtopic (this specific point came from the CEO consult and the user did not object to it — single-item lag gets absorbed by the next day's greedy re-allocation anyway, only a meaningful aggregate impact should surface as a warning).
- **Knapsack-style triage (Phase 5, not yet built)**: rank all subtopics by efficiency (`pointWeight_share ÷ remainingMinutes`), greedily keep the highest-efficiency ones within the time actually available before the test, surface the rest as cut *candidates* (not auto-removed) — framed as "at this pace, finishing everything looks tight; lower-priority candidates:" rather than an imperative "drop this," with the underlying efficiency numbers shown so the suggestion feels evidence-based rather than arbitrary.

### Phase 1 formula revision (2026-07-02, after Phase 4 shipped) — learned per-subject problem-time rates + teacher-hint priority boost

After Phase 4 shipped, the user reviewed Phase 1's original priority/time-estimate formulas (before starting Phase 4.5) and asked for two changes based on their own tutoring/studying experience, refined via `AskUserQuestion` clarification (all recommended options were accepted):

1. **演習1問あたりの所要時間を実測から学習する、教科ごとに**。それまでの `MINUTES_PER_BASIC_PROBLEM`/`MINUTES_PER_ADVANCED_PROBLEM`（3分/6分）は当てずっぽうのままだった置き場だったところ、ユーザー自身の経験則で **13分/25分に変更**した上、セッション記録が貯まれば実測値へ寄せていく仕組みを追加。
2. **先生からのテストのヒントがあった小項目の優先度にボーナスを乗せる**。配点(pointWeight)の均等分配という既存の仕組みは残したまま（廃止案もあったが「均等分配は残し、ヒントで上乗せ」を選択）、ON/OFFチェックボックス1個の追加入力で優先度に倍率をかける。

Implemented via `engineer`, all additive/backward-compatible (no existing call sites break):

- ✅ `src/types.ts` — `ChapterSubtopic.teacherHinted?: boolean` (new, optional).
- ✅ `src/logic.ts`:
  - `MINUTES_PER_BASIC_PROBLEM`/`MINUTES_PER_ADVANCED_PROBLEM` changed 3→13 / 6→25 (still placeholders, now user-informed ones instead of arbitrary guesses).
  - New `learnedProblemRates(sessions, chapters, subjectId)` (+ `LearnedProblemRates` interface, `MIN_SESSIONS_FOR_LEARNED_RATE = 3` placeholder): averages `minutes ÷ completed count` across "pure" sessions for that subject — a session counts only if it recorded *either* basic *or* advanced completions but not both (mixed sessions can't be split into a per-type time, so they're excluded from the learning calc entirely, though they still count normally everywhere else). ### Phase 4 design decision (2026-07-02) — achievement-based, not time-invested-based; registration-date question became moot

Before implementing, ceo and cto subagents were consulted in parallel (per the project's standing workflow) on the one open question carried from Phase 1: what "today" is measured against for the ideal-pace calculation. **They disagreed**: ceo argued for a registration-date-anchored straight-line pace (directly answers "will I make it in time," which is the feature's whole point); cto argued for a 7-day moving window (zero new fields, zero backward-compat cost, but doesn't answer the "in time" question directly). The disagreement was resolved with a synthesis (not picking either agent's side outright): compare a *dynamically recomputed* required pace (`remaining time ÷ days left × 7`) against the last-7-days actual pace — this needs no new field (satisfies cto's risk concern) while still answering "on pace for the deadline" (satisfies ceo's product concern).

**Then the user overrode this whole line of design** (after the synthesis was presented) with a more fundamental correction: pace should be judged by **actual achievement** (understanding level reached, problems actually completed) rather than **time invested** — a student can spend an hour without their understanding moving, or solve problems quickly without spending much time; time-on-task isn't the thing that matters. This made the registration-date-vs-moving-window question moot entirely — neither approach is used, because the final design doesn't compare *time invested* against *time that should have been invested* at all.

Follow-up clarifying questions (asked via `AskUserQuestion`, answers on record) settled the remaining ambiguity in the user's correction:
1. Track **理解度到達度 (understanding-gap) and 演習消化率 (problem-completion) as two separate axes**, not merged into one score — so a chapter can show "understanding: on track, problems: behind" rather than one number that hides which is actually the problem.
2. Use **recent** activity (last ~7 days) to gauge current pace, not an all-time average — reacts faster to a student who just picked the pace back up or just stalled.
3. Phase 4 is **display/warning only** — it does not change what `generateTodayPlan`/`Home.tsx` allocate today. That connection is explicitly Phase 4.5's job (see Phase breakdown above), kept separate because it touches the plan-generation code path directly and the user agreed this should be sequenced after Phase 4 lands cleanly, not bundled into the same change.
4. Problem-count *input* needed to actually be able to compute completion-rate: `StudySession.problemsCompleted` (added in Phase 3, previously a single undifferentiated number) needed a basic/advanced split to make the 消化率 axis meaningful — see `basicProblemsCompleted`/`advancedProblemsCompleted` in the implementation state below.

The understanding axis couldn't be made fully velocity-based like the problem axis, because `Chapter.understanding`/`ChapterSubtopic.understanding` is an EMA-smoothed running value with no stored history — there's no way to reconstruct "understanding 7 days ago" without snapshotting, which nothing in this codebase does (by design — see `decayedUnderstanding`'s "read-time-only, never mutates stored state" pattern used throughout `logic.ts`). The pragmatic compromise, reached without another round of subagent consult since it's a mechanical/technical call rather than a product one: judge the understanding axis by **gap-to-target size**, using **recent session presence** (any session in the last 7 days) as a coarse proxy for "is this actively being worked on" rather than a true derivative. This is called out as an approximation, not hidden as if it were precise.

### Phase 5 confirmed design (2026-07-03) — settled via ceo+cto consult, do not re-litigate

Before writing any code, ceo and cto subagents were consulted in parallel (per the standing workflow) on the four non-obvious design questions. **They converged cleanly**; the user confirmed the release cadence via `AskUserQuestion`. This section is the durable record — resume implementation from here, don't re-derive these.

**Scope: build BOTH (A) forward simulation AND (B) knapsack triage, in one Phase 5** (user confirmed "(A)→(B) を一気に" over an A-first split). ceo's reasoning: (A) alone ("このペースだと詰む" is the one question Phase 4's badges can't answer) leaves a student with anxiety and no remedy — a re-run of the "ask for input, give nothing back" failure; (B) alone has no on-screen context. Both together close the loop on the user's two original motivations: (A) answers "am I spending time optimally?", (B) answers "how do I recover when the plan won't fit?". Build them as a straight (A)→(B) dependency (time-staggered release is *allowed*, but both must finish within Phase 5).

**① Simulation basis — burn-down of remaining-minutes (a scalar), NOT an understanding-growth curve.** The simulation's per-subtopic internal state is *remaining minutes* (a scalar), not understanding. Snapshot each subtopic's `estimateSubtopicRemainingMinutes(subtopic, today, rates).totalMinutes` **once on day 0**, then each simulated day just subtract the minutes allocated. **Do NOT recompute `decayedSubtopicUnderstanding`/re-estimate on future simulated days** — doing so creates a negative-feedback loop (a subtopic not studied on a given day would have its remaining-minutes *grow* via decay, potentially diverging). This also matches how `generateTodayPlan` already works (it only consults decay for *today's* allocation, never for future days), so it's consistent with existing behavior, not a new compromise. Rejected the understanding-growth-curve basis outright: it would reintroduce the exact "minutes → understanding Δ" causal model the user explicitly overrode in Phase 4, need new untuned constants, and duplicate the already-validated `remainingRatio = 1 − decayedSubtopicUnderstanding` model. The registration-date-vs-moving-window question from earlier phases stays moot.

**② Day-by-day iteration — yes.** Iterate day-by-day from today to the latest test date. Each day, take `availableMinutesForDate` and greedily allocate to still-unfinished subtopics by `subtopicPriority`, across all subjects — but a subject drops out of the eligible set once its own test date passes (this per-subject-deadline competition for shared days is exactly what a single totals-comparison can't express: e.g. 数学 test in 3 days vs 理科 in 20 can't pool 理科's days into 数学). This is the `generateTodayPlan` greedy loop wrapped in one outer day-loop — code reuse, not new complexity. Keep the existing per-subtopic per-day `[MIN_SUBTOPIC_SESSION_MINUTES, SESSION_MINUTES]` clamp so the projection stays realistic (also clamp to the subtopic's own remaining so it can't over-allocate past completion).

**③ Chapters without subtopics — excluded from the forecast/triage entirely.** They have no remaining-minutes concept (`generateTodayPlan` models them as a fixed 45 min/day repeated indefinitely; `estimateSubtopicRemainingMinutes` is subtopic-only). A proxy value was rejected — it breaks the dual-path design and makes "never-finishing" chapters permanent bottom-of-triage noise. `simulateForward`/`triageSubtopics` operate on `subtopic !== null` items only. UI adds a one-line "小項目未設定の章はこの見通しの対象外です".

**④ Return interface — new types, separate from `PlanItem`** (`PlanItem` is one day's allocation; this is a multi-day forecast — forcing a shared type would create ambiguous fields):
```ts
interface SubtopicForecast {
  chapterId; subtopicId; subjectId;
  totalMinutesNeeded: number;
  projectedCompletionDate: string | null; // null if not finished by its test date
  shortfallMinutes: number;               // minutes that couldn't be allocated before the test date
  onTrack: boolean;
}
interface SubjectForecastSummary { subjectId; totalShortfallMinutes; atRiskSubtopicIds: string[]; }
interface ForwardSimulationResult { subtopics: SubtopicForecast[]; subjects: SubjectForecastSummary[]; }
```
`triageSubtopics(forecast, ...)` is a separate pure function taking the result (no new stored state) — ranks `shortfallMinutes > 0` subtopics by efficiency (`pointWeight_share ÷ remainingMinutes`) ascending, surfaces the low-efficiency ones as cut *candidates*. The subject summary follows Phase 4's `worstProgressTier` "aggregate then show the overall picture" pattern.

**Display location — Dashboard extension. NOT a new screen, NOT a Home banner.** A 6th screen breaks the settled 5-screen IA (violates "cut before you add"); a Home banner collides "today's one task" with "long-term dread" and reverses the information-density cleanup Phase 4.5 deliberately did (the whole point of `buildDetailLine` returning null for subtopic cards). Dashboard already hosts the Phase 4 pace badges and is where a student goes to "review progress" — the forecast + triage stack naturally below the badges as a "詳しく見る"-style section, zero new navigation to learn.

**Cut-candidate action — informational only; the write-back "exclude from plan" feature is DEFERRED (not in Phase 5).** A "今回は捨てる" toggle that makes `generateTodayPlan` stop emitting a subtopic would add a new "dropped" flag to the data model plus an undo UI (for when the student changes their mind / the test scope changes) — scope creep on the phase the doc itself calls highest-risk. It's also unnecessary: a low-priority subtopic already falls to the back of the next day's greedy re-allocation on its own, so "student sees the candidate and just stops touching it" already works behaviorally. Add explicit exclusion later only if real usage asks for it.

**Psychological framing — these four are REQUIRED design items, not post-hoc polish:**
1. Always conditional phrasing — "今のペースだと" not "間に合いません" (pace is changeable; leave room for agency — a fixed-fate framing only amplifies motivation-(1) anxiety).
2. Always place a "今日のプランを見る" link (→ Home) directly after any bad prediction, so anxiety → next action never breaks.
3. Weak "あくまで目安" tone — the per-problem-minute constants are still placeholders and `learnedProblemRates` falls back to defaults below 3 sessions; reuse Phase 4's "これは近似です" precedent.
4. Frame cut candidates as "時間配分の効率上", never "頑張っていないから" — show the efficiency number to make clear it's arithmetic, not a judgment of the student's effort/ability (the single biggest risk to study motivation if gotten wrong).

**Implementation estimate (cto)**: `logic.ts` gains `simulateForward` (~60–90 lines) + `triageSubtopics` (~30 lines), ~zero new tunable constants, existing functions unchanged. UI is one new component + Dashboard integration (~Phase 4 badge scale). No general-purpose "simulation engine" abstraction — just the greedy allocator wrapped in one more loop.

**When to surface the forecast/triage — CONDITION-BASED, not a fixed days-before-test calendar gate (user chose this over a fixed-window or hybrid option, 2026-07-03).** Show a subject's "間に合わない見込み + 切る候補" section only when BOTH conditions hold:
1. **Meaningful aggregate shortfall** — the subject's total `shortfallMinutes` (summed across its at-risk subtopics) exceeds a threshold (placeholder ~45 min = one study block, tunable like the project's other constants). A single subtopic a few minutes over doesn't trigger it — tomorrow's greedy re-allocation absorbs that. This is the concrete form of the already-recorded "off-track threshold = cumulative impact, not any single lagging subtopic" decision.
2. **Student has started the subject** — at least one session is logged for any subtopic in that subject. Prevents the day-1 false alarm ("registered 20 subtopics → instantly 'you won't finish'"), the same class of problem Phase 4 fixed by capping zero-session subtopics. This gate keys off *evidence of activity, not the calendar* — that's what makes it "condition-based." Once the student is underway, never-started subtopics ARE included honestly in the prediction (a never-touched subtopic close to the test is genuinely at risk and should surface).

**No near-deadline suppression** (deliberately opposite to Phase 4's `PROBLEM_TIER_MIN_DAYS_LEFT = 3` badge cutoff): the forward simulation is a "does the remaining work fit the remaining available time" check, which gets *more* reliable as the test approaches, and triage is *most* useful right before the test (the "plan is falling apart, help me triage" moment that is the user's core motivation). So triage stays visible all the way to the test day. The rationale for why triage differs from the Phase 4 badge here: the badge extrapolates recent velocity (spikes/unreliable near the deadline), whereas the simulation compares totals (tightens near the deadline).
