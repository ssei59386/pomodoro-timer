# Feature history: 暗記科目対応（英語・国語・社会）

「見通し」機能（`docs/feature-mitoshi.md`）が数学・理科向けにPhase 1〜5まで完成したのを受けて、2026-07-03にユーザーから提起された次の大きな方向転換。**英語（単語帳＋教科書）は実装完了（2026-07-03）**。国語・社会は未着手。

## 背景・ユーザーの動機

CLAUDE.mdのPhase 0スコープには「全5教科への対応」「暗記科目モード」が明示的に範囲外として書かれていた。ユーザーは、数学・理科向けの「見通し」機能が一区切りついたタイミングで、定期テストに限って英語・国語・社会（＝暗記科目）にも対応したいと提起。理由：これらは数学のような「理解度を上げる」アプローチとは根本的に異なるアプローチが必要なはず、という認識。

この後、実際に身近な人（開発者本人ではない人）にアプリを使ってもらう計画。

## CEO/CTO consult (2026-07-03) と ユーザーの上書き — 蒸し返さないこと

標準ワークフローに従い、コードを書く前にceo/ctoに相談した。

**ceoの結論**：先に数学・理科版だけの現状を身近な人に使ってもらい、フィードバックを得てから暗記科目に着手すべき（CLAUDE.mdの「Ship-quality polish beats new features」に合致）。今日Phase 5が終わったばかりで、開発者以外がこのアプリを使った実績はまだゼロ。CLAUDE.mdのPhase 0範囲外条項の趣旨（未完成機能を中途半端に見せるな）からすれば、Phase 0を終えてPhase 1として暗記科目を設計すること自体は筋が通るが、今のタイミングでやるべきではない、という意見。

**ctoの結論**：暗記科目は既存の`Chapter`/`ChapterSubtopic`（0〜1の連続的な理解度を前提）にそのまま乗せられない。暗記は「覚えた/忘れた」に近い二値で、本質的に間隔反復（spaced repetition、代表的アルゴリズムにSM-2やLeitner system）が必要。新しいデータの単位（例：`MemoryItem`/`Deck`）を新設する必要があり、実装コストは中〜大。英語・国語・社会を一気に3教科作るのではなく、まず1教科・最小限のモデルで検証すべき規模、という意見。既存の忘却曲線（`decayedUnderstanding`、read-time-onlyでstorageを書き換えない設計思想）自体は転用できるが、スコアリング・優先度の主軸は「配点」ではなく「次に忘れるタイミングの予測」に置き換わるべきとのこと。

**ユーザーは「先に人に使ってもらう」という提案を明示的に上書きし、予定通り暗記科目の設計を先に進めることを選択した（2026-07-03、AskUserQuestion経由）。** 実装順序としてはユーザーの判断を尊重し、暗記科目の設計・実装を先に進める。「まず人に使わせるべき」という提案を将来のセッションで再度持ち出さないこと——ユーザーは一度検討した上で明確に却下している。

なお、ctoの「1教科・最小モデルから始めるべき」という提案自体は、ユーザーはまだ明示的に上書きしていない（「先に人に見せるか」の順序についてのみ判断した）。次のセッションでこの点をユーザーに確認してから設計に入ること。

## Status: 設計確定（2026-07-03）— 英語（単語）から着手、実装はごく小規模

### 着手教科の決定
cto提案（3教科一気ではなく1教科・最小モデルで検証）に対し、ユーザーは**英語（単語）**を選択（AskUserQuestion、2026-07-03）。国語・社会は英語で得た知見を踏まえて後日判断。

### 第一段の技術・UX consult（cto/ceo並行、2026-07-03）— 前提が変わり一部супersede
この段階では「単語を個別登録し、本物の間隔反復（spaced repetition）で1語ずつ復習日を管理する」前提でconsultした。結論：
- アルゴリズムはSM-2ではなくLeitner方式の簡易版（箱1〜5、固定の復習間隔テーブル）。
- 「今日のプラン」への統合方法は cto（別区画）と ceo（既存リストに統合）で意見が割れた。
- 登録は「単語,意味」の一括貼り付け、カリキュラム参考データは著作権リスクのため作らない。
- クイズ的なセッション記録UIが新規に必要。

**この consult は個別単語登録を前提にしていたが、ユーザーがその後の質問で「個別登録は非現実的、単語数だけ入力する数学の問題数と同じ方式にしたい」と明確に選択したため、上記の一部（特にLeitner箱・MemoryItem型・専用クイズUI）は不要になった。** 「今日のプランへの統合」論点についてのみ、ユーザーは折衷案（内部計算は別、見た目は1つのリスト）を選んだが、後述の通りこの論点自体も実質解消される。

### 確定設計（数だけ登録方式に決定した後の再検討、2026-07-03）— 実装はほぼゼロ

ユーザーが「単語を個別登録せず、数（例：50語）だけ入力する」という数学の`basicProblems`/`advancedProblems`と同じ方式を選んだ結果、**単語暗記は新しいデータモデル・新しいロジックを一切必要としない**ことが判明した（`src/types.ts`を確認して検証済み）：

- `ChapterSubtopic`には既に`basicProblems`/`advancedProblems`という**数だけを持つフィールド**がある。単語数もここにそのまま乗る（例：小項目名「Lesson 5 単語」、`basicProblems`＝単語数）。
- `StudySession`には既に`correctRate`（正答率）・`selfReport`（自己評価）がある。単語の小テスト結果（「30語中24語正解」）はそのまま`correctRate`に記録すれば、既存の理解度更新式（§6.1）がそのまま使える。
- 忘却曲線・優先度スコア・今日のプラン生成（`generateTodayPlan`）・見通し機能（Phase 4のペースバッジ、Phase 5の前向きシミュレーション＋トリアージ）は、教科の中身が数学か英単語かを区別しない実装になっている。小項目（subtopics）を使えば英語もPhase 4/5の恩恵をそのまま受けられる。
- **v1では小項目は使わず、章レベルのみで十分**と判断（推奨、cto/ceo再consult不要なほど明確）。理由：単語の登録粒度は「レッスン単位」がおそらく自然で、それは`Chapter`そのものに対応する。小項目まで割る必要が出てきたら後で追加すればよい（既存のデュアルパス設計がそのまま使える）。この場合、章は配点(`pointWeight`)・初期理解度（自己申告）・セッション記録という既存の「小項目なし章」の経路をそのまま通る。単語数は`ChapterMetadata.exerciseCount`（既存の情報表示専用フィールド）に「単語数」として入れておけば十分（スコアリングには使われないが、生徒が見返す用の情報として）。

**唯一必要な変更：`Onboarding.tsx`に英語を3つ目の教科として追加する。** 現状`SubjectKey`型が`"math" | "science"`にハードコードされている（テスト日入力欄・章追加ボタン・教科選択プルダウンがそれぞれ2教科決め打ち）ため、ここに`"english"`を足すUI変更が必要。`src/types.ts`・`src/logic.ts`は無変更。`Settings.tsx`のカリキュラムサジェスト表示条件（`subject.name === "数学" || "理科"`）も英語には該当しないだけで正しく動く（英語向けカリキュラム参考データは著作権リスクのため作らない方針と一貫）。

**忘却の速さ（半減期）は数学と同じ21日のままv1では変更しない。** 単語は本来もっと速く忘れるはずだが、教科ごとに調整可能にするのは今は過剰実装（CLAUDE.mdの「先回り実装反対」方針）。実際に人に使ってもらってから、必要なら調整する。

### 【superseded】上記の「実装ほぼゼロ」案は英単語には不採用。教科書長文・文法ワークには引き続き適用

ユーザーからの追加情報（2026-07-03）：実際の定期テストの単語範囲は単語帳300語以上＋教科書40語程度で、これを1語ずつ意味まで手入力させたら「ほぼ100%のユーザーが離脱する」。上記の「章レベル・数だけ入力」案は**英単語には不適用**と判断（章＝レッスン単位という粒度では「どの単語を復習すべきか」を全く指示できないため、忘却対策にならない）。ただし**教科書の長文読解・文法ワークについては元の「実装ほぼゼロ」案のまま**（数学と同じ章モデルを流用、変更不要）。

### 確定設計 v2（2026-07-03）— 単語は「番号（インデックス）」で個別管理、テキストは保存しない

一度「個別登録（テキスト入力）→非現実的」「数だけ入力→どの単語か分からない」「匿名の束→ceo/ctoに却下（生徒の自己管理が壊れると指示が空回りする）」と巡った末、ユーザー自身が出した解決策：**単語の意味テキストは一切保存せず、単語帳の見出し番号・教科書レッスン内の通し番号という「番号」だけで個々の単語を識別する。**

- **単語帳（例：ターゲット1900など）**：範囲（例：「371〜670番」）を1回入力するだけで、アプリが371〜670の各番号を個別の学習アイテムとして自動生成する。単語の意味は一切入力させない。
- **教科書**：既存の`Chapter`（レッスン単位）に紐づけて、そのレッスン内の通し番号（1〜40番など）で管理する。
- 個々のアイテムはLeitner方式（cto提案の簡易間隔反復。箱1〜5、固定の復習間隔テーブル）で管理し、「わかった/わからなかった」を番号ごとに記録して次の復習タイミングを計算する。
- **これは最初に却下された「匿名バッチ」案とは違う。** 番号という永続的な識別子があるため、アプリは「371番の次の復習日はいつか」を個別に正確に覚えていられる——生徒が「どれが復習対象か」を自分の記憶で管理する必要がない（このexactな理由で匿名バッチ案はceo/ctoに却下されていた。番号管理はその欠陥を解消する）。
- **新規単語の1日あたりのペース**：アプリが自動計算する（残り未着手数 ÷ テストまでの残り日数、既存の`daysLeft`を再利用）。ユーザーが毎日手入力する必要はない。
- **復習の見せ方**：「今日は371〜420番のうち、前回わからなかった分を復習してください」のように、範囲＋わからなかった分、という形で提示する（ユーザー確認済み、2026-07-03）。

**データモデル案（実装時に細部は engineer の判断に委ねる）**：
```ts
interface VocabRange {
  id: string; subjectId: string; label: string; // 例:「ターゲット1900」
  chapterId?: string; // 教科書レッスンに紐づく場合のみ
  startNumber: number; endNumber: number;
}
interface VocabItem {
  id: string; rangeId: string; number: number;
  introduced: boolean; box: 0 | 1 | 2 | 3 | 4 | 5; // 0=未着手
  nextReviewDate: string | null;
}
```
新規ロジック関数（案）：`BOX_INTERVAL_DAYS`定数、`getTodaysVocabPlan(ranges, items, sessions, today)`（新規導入分＋復習due分を返す）、`advanceVocabBox(item, wasCorrect, today)`（Leitner箱の昇降）。既存の`generateTodayPlan`・`Chapter`/`StudySession`は無変更（単語は完全に別のロジック系統）。

**Home画面での見せ方**：既存の「今日やることリスト」に、英単語も他の章と同列の1項目として並べる（ceo当初案の通り。cto提案の「別区画」は今回は採用しない——単語がリストの1項目としてシンプルに並ぶ方が良い、という元々の判断を維持）。

## 確定設計 v3（2026-07-03）— 単語単位から「固定20語ずつの枠」単位へ移行

実際の単語帳は300語以上あり、v2（単語1つずつをVocabItem/Leitner箱で個別管理）のまま実装すると、生徒が単語1つずつ「わかった/わからなかった」をタップする必要があり、負担が大きすぎるとユーザーが判断した。cto相談済み（実装コストは半日〜1日規模、コード量はむしろ減る方向という評価）。

### 変更内容
- 単語1つずつではなく、範囲を**固定20語ずつの「枠」**（`VocabChunk`、`VOCAB_CHUNK_SIZE = 20`）に分割し、枠単位でLeitner管理する。端数処理：最後の枠が5語未満になる場合は直前の枠と合算（極端に短い枠を避ける）。5〜19語の端数はそのまま独立した最後の枠にする。
- 生徒は実際の勉強（単語帳・教科書を見て覚える）を紙の上で行い、わからなかった単語には自分で単語帳の余白に印をつける（アプリには単語の中身を一切入力させない、という v2 からの方針は維持）。
- アプリの役目は「この枠（例：381〜400番）は今日が復習のタイミングです」と枠単位で思い出させることだけ。
- 理解度の段階評価（0〜1の連続値、自己申告5段階、正答率）は一切持ち込まない。**枠の状態は「復習継続中（まだ完璧じゃないと仮定）」か「完了（生徒が完璧になったと明示的に報告）」の二値だけ**（`completed: boolean`）。
- 復習継続中の枠は、既存のLeitner箱の間隔（`VOCAB_BOX_INTERVAL_DAYS`、箱1〜5）をそのまま流用する。生徒が「まだ完璧じゃない」と答えるたびに箱を1つ進めて次の復習間隔を伸ばす（v2にあった「不正解なら箱1に戻す」という正誤判定に基づくリセットは廃止——v3では正誤の概念自体を持ち込まない）。「完璧になった」と答えた枠だけ `completed: true` になり、ローテーションから外れる（出題対象を集める `getTodaysVocabChunks` 側で `completed` をフィルタする。box/nextReviewDateは完了後もそのまま残す）。
- 個々の単語番号ごとのbox/nextReviewDateは廃止。**枠（chunk）ごとに1つのbox/nextReviewDate**を持つ。
- 新規の枠を1日に何枠ずつ導入するかは、既存の考え方（残り未着手枠数 ÷ テストまでの残り日数）をそのまま流用（`calculateDailyNewVocabPace`、母数が「単語数」から「枠数」に変わっただけ）。

### 実装
- `src/types.ts`：`VocabItem` を削除し `VocabChunk`（`startNumber`/`endNumber`/`introduced`/`box`/`nextReviewDate`/`completed`）に置き換え。`AppData.vocabItems` → `AppData.vocabChunks`。
- `src/logic.ts`：`generateVocabItemsForRange` → `generateChunksForRange`（20語ずつ分割＋端数合算）。`advanceVocabItem` → `advanceVocabChunk`（正誤判定を持たず、常に箱を1つ進める設計に変更）。新規に `completeVocabChunk`（completedをtrueにするだけ）。`calculateDailyNewVocabPace`／`getTodaysVocabItems`（→`getTodaysVocabChunks`）は枠ベースに書き換え、`completed` な枠を新規・復習どちらの出題対象からも除外するガードを追加。`estimateVocabMinutes` は「枠数」を受け取り、内部で `VOCAB_CHUNK_SIZE` 倍して語数換算してから見積もる。
- `src/components/VocabQuiz.tsx`：全面書き換え。ボタンを「わかった/わからなかった」（正誤フレーミング）から「まだ完璧じゃない/完璧になった」（達成度合いの自己申告フレーミング）に変更。表示も番号1つではなく範囲（開始〜終了番号）単位。
- `src/store.tsx`：`recordVocabAnswer` を削除し、`advanceVocabChunk`/`completeVocabChunk` の2アクションに置き換え。`addVocabRange`/`removeVocabRange` は内部で扱うデータが枠に変わっただけで責務は変わらず。
- `src/components/Home.tsx`／`Dashboard.tsx`：件数表示を「問」から「枠」に変更。Dashboardの単語帳進捗は「5回連続正解した語の数」から「完了した枠の数／全枠数」に変更（枠単位・二値設計に合わせる）。
