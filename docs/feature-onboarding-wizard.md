# （設計記録）オンボーディングの「軽量ウィザード化」

**Status: 設計確定（2026-07-06）→ 上記のとおり本格版として実装完了。**

このファイルは、オンボーディング画面（`src/components/Onboarding.tsx`、アプリで一番複雑なフォーム）を作り替えるタスクの確定設計をまとめたもの。ceo・cto・ux-reviewer の3体に設計相談をかけ、方針が確定した状態でユーザーから「もうやっちゃってほしい。できるでしょ。でもチャット変えるから引継ぎして」と実装ゴーサインが出た（前セッションでは引き継ぎのみ、実装は次セッション）。

**スコープはユーザーが「本格版」を明確に指定した。** Q&A では軽量版を推奨として提示したが、ユーザーは直後に「本格版でやってほしい」と3回上書きした。よって**ワイヤーフレーム通りの本格ウィザード**（1画面ずつ完全に区切るステップ式）で実装する。3体は軽量版を推奨したが、これはユーザー判断で覆っている——**この決定を蒸し返さないこと。** 3体レビューで挙がった個別の論点（下書き永続化・ステップごとバリデーション・使う教科を先に選ばせる等）は本格版でこそ重要度が上がるので、下記にすべて統合してある。

## 背景・目的

現状の `Onboarding.tsx` は「全教科（数学・理科・英語・社会・国語）のテスト日・章・暗記範囲・週の予定・カレンダー例外を1画面に縦ヅラで全部並べる」単一フォーム。「テスト日入力欄が5教科分ずらっと並んで画面がとても長い」問題は ux-reviewer が過去に複数回指摘し、2回意図的に見送られてきた既知のバックログ項目。今回ユーザー自身が実機で気づいて手書きワイヤーフレームを持参し、作り替えを要望した。CLAUDE.md の Product direction 軸1・3（既存journeyの磨き込み、最初の数分の離脱潰し）に正面から該当する。

ユーザーのワイヤーフレーム原案（本格ウィザード）：①テスト日を登録（＋で教科追加）→②教科ごとに章・小項目を入力→③教科ごと確定して次の教科へ、全教科終わったら完了→④週の予定→⑤カレンダーで例外日。

## 確定方針：本格ウィザード（ユーザー選択）

ワイヤーフレーム通り、**1画面ずつ完全に区切るステップ式ウィザード**として実装する。ユーザーの明確な指定。3体は「軽量版で十分」を推奨したが覆っている（蒸し返さない）。

**ステップ構成（ワイヤーフレーム準拠＋cto/uxの補正）：**

0. **使う教科を選ぶ**（ワイヤーフレームには明示されていないが cto 指摘により必須）。現状ロジックは「章か暗記範囲を登録した教科だけを Subject 採用」＝使用教科を後段の入力から逆算している（`Onboarding.tsx` L255-269）。本格ウィザードで①にテスト日を先に置くなら、ここで使用教科を確定させないと「①でテスト日を入れた教科を②でスキップ→黙って捨てられる（＝入力したのに消えた）」体験になる。チェックボックスで使う教科を選ばせ、以降のステップは選んだ教科だけを対象にする。既存の教科key定数（`SUBJECT_LABELS` / `CHAPTER_CAPABLE_SUBJECT_KEYS` / `VOCAB_SUBJECT_KEYS`）を流用。この0ステップが「テスト日欄が5教科分ずらっと」問題の根本解決にもなる。
1. **テスト日を登録**（0で選んだ教科分だけ）。**＋で複数テスト日を後から足しやすい形にしておく**（複数テスト日の本対応は後回しだが、入力欄の構造だけ手戻り防止しておく）。
2-3. **教科ごとに章・小項目・暗記範囲を入力**（1教科ずつ、確定して次の教科へ）。「教科 2/3」のようなその場の進捗表示を出す。**「章か暗記範囲どちらか一方でOK」の必須緩和（`Onboarding.tsx` L238-246）は各教科ステップに引き継ぐ。** ワイヤーフレームの②③がここ。
4. **週の予定**（`WeeklyScheduleEditor` をそのまま流用）。
5. **カレンダーで例外日**（`CalendarOverrides` / `DateOverridesList` をそのまま流用。UI自体は作り直さない）。
6. **確認画面**（読み取り専用サマリー：教科・テスト日・章数・暗記範囲数・週合計勉強時間・例外日数を一覧、各項目に「編集」で該当ステップへ戻れる）。本格ウィザードで失う「全体を一覧できる／後から自由に直せる」自由さの埋め合わせ。実装コストは低い（既存stateの表示だけ）。

**本格版で必須になる追加実装（3体レビュー由来、本格版ほど重要度が高い）：**

- **戻る/次への状態管理**とステップ遷移。1コンポーネント内で state を保持したまま条件レンダリングを切り替える形なら入力保持は自動（ステップを key 付きで条件レンダリングしない限りアンマウントが起きない）。ただし930行超の現状に足すので、ステップごとに `OnboardingStepXxx.tsx` へ分けるのが妥当（既存の「親state・子はvalue/onChange」パターンを踏襲、新規パターンは持ち込まない）。
- **ステップ間の下書き永続化（必須）。** 現状は最終送信（`completeOnboarding`）まで localStorage に一切書かない。本格版はステップ＋教科ループに分割され完了までの所要時間・中断確率が最も高いので、**本番キーとは別のドラフト用localStorageキー**に各ステップ移動時に保存し、途中でタブを閉じても再開できるようにする。これが無いと本格ウィザードは離脱率を悪化させる。
- **ステップごとバリデーション。** 現状 `handleSubmit`（L230-349）は全項目を最後にまとめて検証し `scrollToSection` で誘導。これを持ち越すと「5ステップ埋めた後に①が無効と戻される」最悪体験になる。各ステップの「次へ」タップ時にそのステップだけ検証する形へ。`scrollToSection` はステップ内エラー表示に転用できる。「次へ」は disabled 一辺倒にせず、既存の `error-inline` パターン（タップ可能＋即時インラインエラー）に合わせる。
- **`metadata-block`（演習問題数・学習範囲・難易度、`Onboarding.tsx` L587-643 付近）を Onboarding から削り Settings専用に。** 2回見送られたバックログ項目。本格版は教科ごとに最大5回繰り返すぶん密度負荷が単一ページ時より増すので、この機会に解消（ceo・ux 推奨）。

## スコープに含めない（今回やらない）

- **「1教科に複数テスト日」（例：数学が代数と幾何で試験日が別日）は今回は切り離して後回し。** 3体全員一致。理由：これはUIだけでなくデータの持ち方（現状 `Subject.testDate` は単数）を変える必要があり、`logic.ts` の `proximity`/`priority`/`daysLeft`/`generateTodayPlan`/`simulateForward`/`shouldSurfaceForecastForSubject` と、Settings/Dashboard/Home の「教科名＋テスト日」表示まで波及する中〜大規模の変更。大多数のケースは1教科1テスト日でコアjourneyを止めていない。英語→社会展開と同じく「まず軽量ウィザードを実運用してから判断」。
  - **ただし手戻り防止のため、テスト日入力欄は「＋ テスト日を追加」を後から足しやすい形で作っておく**（cto・ux）。単一テストのケース（大多数）では追加の手間ゼロを保つ設計にする。
  - 将来やるときの推奨データモデル（cto検証済み）：**案1 = `Chapter` ごとに `testDate?: string` を持たせ、`Subject.testDate` はフォールバック/デフォルトとして存続**（`VocabRange` は `chapterId` が任意で、章に紐付かない暗記範囲があるため `Subject.testDate` は廃止できない）。`logic.ts` の日付を使う関数群は既に引数ベースで汎用化されており、「日付の解決元を `chapter.testDate ?? subject.testDate` に差し替える」機械的作業で済む。案2b（Subject自体を「数学(代数)」等に複製）は logic.ts 無傷に見えるが、閉じた `SubjectKey` union 型の前提を壊すので不採用。

## 実装ガイド（cto検証）

- **ステップ番号 state で足りる**（コンポーネント分割は必須ではないが、`Onboarding.tsx` は既に930行超なので、ステップごとに `OnboardingStepXxx.tsx` へ分けるのが妥当）。分割する場合は既存の「親がstate、子は value/onChange の制御コンポーネント」パターン（`WeeklyScheduleEditor`/`DateOverridesList` と同型）を踏襲する。新規パターンは持ち込まない。
- **入力保持は自動**：1コンポーネント内で state を保持したまま条件レンダリングを切り替えるだけなら、アンマウントが起きないので保持される（ステップを key 付きで条件レンダリングしない限り）。
- **順序の矛盾に注意**：現状ロジックは「どの教科を使うか」を②の章・暗記範囲の入力結果から逆算している（`Onboarding.tsx` L255-269 の `usedMath`/`usedScience`... 判定 = 章か暗記範囲を実際に登録した教科だけを Subject として採用）。①でテスト日を先に聞く構成にするなら、**「まず使う教科を選ぶ」ステップで使用教科を確定させる**設計に変える必要がある。そうしないと「①でテスト日を入れた教科を②でスキップ → 黙って捨てられる」（＝「入力したのに消えた」）という体験になる。
- **バリデーションはステップごとに**：現状 `handleSubmit`（L230-349）はテスト日・週間予定・カレンダー例外・暗記範囲を最後にまとめて検証し `scrollToSection` で誘導。これをそのまま持ち越すと「5ステップ全部埋めた後に①の入力が無効と戻される」最悪の体験になる。各ステップの「次へ」タップ時にそのステップだけを検証する形へ。`scrollToSection` パターンはステップ内エラー表示にそのまま転用できる良い土台。
- **④⑤の既存部品はほぼ無改修で流用可**（`Onboarding.tsx` L507-513, 523-524 で既に完結して呼ばれている）。
- **規模：中〜大規模（本格版のため）。** 影響は `Onboarding.tsx` とその専用テスト（`Onboarding.test.tsx`、fill/assert が多くステップ遷移を挟む形への書き直しが機械的だが件数多め）にほぼ閉じ、`logic.ts`・`store.tsx`・`types.ts` は無傷（複数テスト日を後回しにする限り）。ただし本格版は軽量版に上乗せで「ステップ遷移の状態管理」「下書き永続化（新規のドラフト用storage経路）」「ステップごとバリデーションへの再構成」が加わるぶん、cto の当初見立て（軽量版で中規模）より一段上の中〜大規模。`storage.ts` にドラフト保存/復元の経路を足す可能性がある（本番の `study-planner-data-v1` とは別キー）。

## UX注意点（ux-reviewer）

- **ステップ間の下書き永続化を入れる**（重要）。現状は最終送信（`completeOnboarding`）まで localStorage に一切書かない。ステップ＋教科ループに分割すると完了までの所要時間・中断確率が増えるので、**本番キーとは別のドラフト用キー**に各ステップ移動時に保存し、途中でタブを閉じても再開できるようにしないと、ウィザード化がむしろ離脱率を悪化させる。
- **教科ループ疲労の緩和**：使う教科を最初に絞る（上記の骨格1）＋各ループに「教科 2/3」のようなその場の進捗表示。フェーズ表示＋教科内カウントの二段構成を推奨（絶対ステップ数カウンタは動的に変わって逆に不安になる）。
- **「次へ」ブロックは disabled 一辺倒にしない**：既存の `error-inline` パターン（`DateOverridesList.tsx` L106-108、`CalendarOverrides` の `invalid` 表示）＝タップ可能＋即時インラインエラーに合わせる。中高生には「押せない」だけでは理由が伝わらない。
- **複数テスト日入力の見せ方（将来）**：教科ごとに「＋ テスト日を追加」で名前付きテスト（例：数学(代数) 7/10・数学(幾何) 7/12）を作れる形。②の章登録時に「この章はどのテストに出ますか」を選ばせる（テストが1つの教科ではこの選択自体を出さず今と同じ手数を維持）。
- **各ステップの必須/任意を明示**：現状「任意」バッジは「特別な予定」セクションのみ（`optional-badge`）。各ステップで一貫適用し「飛ばせる」を視覚化。
- **`.icon-btn`（✕削除ボタン）のタップ領域が44px未満**（`styles.css` L256-263、`min-height` 指定なし）。章・小項目・暗記範囲・時間帯の削除で繰り返し登場するので、この機会に底上げ。
- **Androidの物理戻る/スワイプバック**がウィザードの「1つ前へ」になるかアプリ離脱になるか、実機確認が必要（PWAの落とし穴）。方針を設計段階で決める。
